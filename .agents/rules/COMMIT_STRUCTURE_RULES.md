# Правила структуры коммитов

Все изменения одной задачи оформляй одним итоговым коммитом. Включай в него
спецификации OpenSpec, ADR, проектные правила, документацию, продуктовый код,
тесты и связанные файлы, если они относятся к этой задаче.

Не разделяй задачу на коммиты по категориям файлов, слоям, подфичам или этапам
разработки. Сообщение единственного коммита должно описывать результат задачи
и соответствовать всему его diff.

Порядок разработки изменения поведения определяется
[правилами OpenSpec](OPENSPEC_RULES.md): **спецификация → падающий тест →
реализация → зелёный тест**. Все эти этапы входят в один итоговый коммит.

Перед публикацией объедини локальные промежуточные `WIP`, `fixup` и другие
коммиты текущей задачи в один. Уже опубликованную историю не переписывай
без явного указания пользователя.

## Критерии самопроверки

1. Все изменения текущей задачи собраны в одном итоговом коммите.
2. Сообщение коммита описывает результат и соответствует его содержимому.
3. В коммит включены только относящиеся к задаче изменения.
4. Итоговое состояние прошло применимые проверки: валидацию спецификаций,
   проверку документации, а при наличии кода — сборку и тесты.
