## Context

Мотивация и границы — в [proposal.md](proposal.md). Реализация игры отсутствует:
проверены `lib/main.dart`, `test/widget_test.dart` и каталог OpenSpec.
Текущая работа — подготовка контракта, не выпуск игрового движка.

## Goals / Non-Goals

**Goals:** воспроизводимая доменная модель, однократный расчёт результата,
различение трёх видов очков, возможность проверить правила без Flutter UI.

**Non-Goals:** выбор экранов, транспорта, формата сохранения, алгоритма бота
и генератора случайных чисел. Эти решения не нужны для проверки правил
по заданным раздачам и действиям.

## Decisions

### D1 — Один именованный профиль

Нормативное поведение задаёт [спецификация](specs/kozel-rules/spec.md).
Ссылки на интернет объясняют происхождение, но изменение внешней страницы
не меняет уже принятую версию профиля. Альтернатива с независимыми переключателями
каждого дворового правила породила бы непроверенные комбинации и не нужна
для согласованного состава игры.

Пользователь выбрал основу DominoK и отдельно подтвердил следующие уточнения:

| Вопрос | Принятое решение | Требование |
|---|---|---|
| Несыгранный подходящий дубль | Игра продолжается до отсутствия ходов | R5 |
| Рыбак после дубля | Последний выложивший недублевый камень | R6 |
| Единственный 0–0 | 10 очков у любого игрока, также при сравнении на рыбе | R7 |
| Повторные яйца | Общий перенос накапливается до определённого проигрыша | R9 |
| Забор при ничьей | Сохраняется у обеих команд | R9, R10 |
| Открытие счёта после яиц | Только собственный остаток кона от 13; при меньшем остатке и отсутствии записи весь штраф с яйцами идёт на забор | R10 |

Последняя строка — явное уточнение пользователя, а не утверждение о полноте
текста DominoK. Оно исключает вариант открытия по сумме остатка и переноса.
Спортивная ничья с нулём и ранняя рыба из Keft не входят в профиль.

### D2 — Детерминированные переходы

Партия представляется неизменяемым снимком. Операция принимает явное действие
и возвращает новый снимок либо ошибку. Бизнес-правила реализуются методами
объектов с явными зависимостями. Глобальный изменяемый счёт и вычисления внутри
виджетов исключаются: они затрудняют воспроизведение конкретного кона.

Роли разделены в таблице proposal. Не нужны Repository, сервер или хранилище:
на данном этапе отсутствует соответствующая обязанность. Вызывающая сторона
подаёт действия последовательно; фоновых задач и подписок у модели нет.

### D3 — Камень и его ориентация

Идентичность — неупорядоченная пара; ориентация относится к положению в цепочке.
При разборе 5–2 нормализуется в тот же камень, что 2–5. Геометрия изгибов цепи
не влияет на допустимые ходы. Альтернатива с координатами экрана внутри правил
ошибочно связала бы правила с шириной окна.

### D4 — Явная раздача вместо скрытой случайности

Правила принимают перестановку набора, распределяемую циклически по местам.
Будущий вызывающий код может заранее перемешивать набор; случайность внутри
проверки ходов не требуется. Недопустимая по игровому ограничению раздача
возвращает запрос пересдачи, а не запускает бесконечный внутренний цикл.
Следующая предоставленная раздача позволяет продолжить работу.

### D5 — Раздельные счётчики

Для команды отдельно хранятся записанный счёт и предварительная сумма
«на заборе»; общий перенос «яиц» принадлежит партии. Нулевой записанный счёт означает,
что команда ещё не открылась. Один общий числовой счёт не может представить
отыгрыш предварительных очков без случайного списания уже записанных.

Результат кона содержит причину завершения, остатки обеих команд, победителя
и проигравшего либо признак ничьей, значения до/после расчёта и право захода.
Он создаётся вместе с терминальным переходом; повторная обработка завершённого
кона не должна начислять штраф ещё раз.

Порог проверяется по собственному остатку текущего кона до прибавления
забора и яиц. Ветвь назначения определяет R10: сначала выбирается запись
или забор, затем туда попадает сумма с переносом; общий перенос очищается.
Если яйца попали на забор, они становятся частью отыгрываемой суммы команды
и перестают быть общим переносом. Таблица R10 — единственный нормативный
источник формул, чтобы не поддерживать две расходящиеся версии подсчёта.

Фазы модели: ожидание первой раздачи → розыгрыш → результат кона либо
результат партии. Из результата кона возможна следующая раздача; неудачная
попытка раздачи сохраняет эту фазу. Из результата партии продолжить ту же
партию нельзя. Новая партия — отдельная модель с нулевыми счётчиками.

### D6 — Проверка инвариантов

В принятом кону объединение рук и цепочки равно полному набору, пересечения
пусты. Каждый допустимый ход уменьшает число камней на руках на один; пас —
на ноль. Сумма обычных номиналов всегда 168; штрафное правило пустого дубля
не изменяет этот инвариант физического набора.

Проверка выхода предшествует проверке рыбы. Для текущего профиля достаточно
вычислить допустимые ходы всех рук; эвристика «концы равны» неверна. Она
пропускает несыгранные камни серии и оставшийся дубль.

Контрольная раздача для R5.3–R5.4 (кон после первой записи, заходит P0):

| Место | Начальная рука |
|---|---|
| P0 | 0–2, 3–4, 2–6, 0–0, 0–6, 1–5, 3–6 |
| P1 | 0–1, 2–4, 2–2, 0–3, 1–1, 1–6, 4–4 |
| P2 | 1–2, 2–5, 0–4, 1–3, 3–3, 4–5, 5–5 |
| P3 | 2–3, 5–6, 0–5, 1–4, 3–5, 4–6, 6–6 |

Циклическая последовательность выкладок P0 → P1 → P2 → P3:
0–2 (ориентация 2–0), 0–1, 1–2, 2–3, 3–4, 2–4, 2–5, 5–6, 2–6, 2–2.
Все камни после первого добавляются справа подходящей половинкой.
После девятого камня ещё допустим 2–2; после десятого ходов нет.
Остатки A = 54, B = 60. Все 28 камней различны; ограничений для пересдачи нет.
Это самостоятельно составленный проверочный пример, а не цитата из источника.

## Risks / Trade-offs

- Разные дворовые варианты под одним названием → фиксированный профиль,
  [сопоставление источников](../../../../docs/research/kozel-fish-eggs-sources.md)
  и явная история согласования правил.
- Ошибка между предварительным счётом и переносом → отдельные поля,
  таблица переходов и тесты последовательностей конов.
- Синтетический тест рыбы с невозможными руками → полные валидные раздачи
  для интегральных сценариев; арифметические таблицы отдельно проверяют расчёт.
- Многократная неудачная раздача → явный результат пересдачи без зависания;
  статистическое качество перемешивания относится к будущему источнику раздач.

## Migration Plan

Данных игры и действующего контракта пока нет, миграция не требуется.
После согласования план реализуется через падающие тесты и проверку результата.
Подключение к веб-интерфейсу потребует отдельного изменения.
Основные спецификации обновляются только при завершении и архивировании
реализованного изменения штатным процессом проекта.
